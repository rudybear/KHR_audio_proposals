# Drum Kit — End-to-End Playable glTF Asset (Plan)

Goal: a single glTF asset where a user plays a musical instrument **purely from spec**: 3D drum kit model + `KHR_audio_emitter` (sounds, spatial placement) + `KHR_audio_environment` (room, sends) + `KHR_interactivity` (hit detection → sound triggering). The flagship demo for the layered audio architecture — and a living testbed for feedback item **E1** (event-driven playback), since "play a one-shot on interaction" is exactly what the current specs cannot express portably.

## Proof of concept: DONE (2026-08-02)

`gltf-webgpu` branch `feature/khr-audio` already contains the mechanism end-to-end:
- `examples/audio-demo/drum-pads.gltf` — three colored pads; clicking one fires `event/onSelect` → `pointer/set` of `/extensions/KHR_audio_emitter/sources/{i}/playing` → the viewer's audio bridge fires a one-shot through the emitter's positional chain (HRTF, air absorption, mediumRoom reverb send).
- Regenerate with `node scripts/make-audio-demo.mjs`; open `viewer.html?model=/examples/audio-demo/drum-pads.gltf`, click **Audio**, click pads.
- The `playing` pointer is **not spec** — it is deliberately a prototype extension of the Object Model, to be cited in the E1 feedback ("here is the one-line pointer that makes assets playable; standardize this or give us interactivity verbs").

## Status update (2026-08-02, later): v1 kit SHIPPED

`examples/drum-kit/drum-kit.gltf` (gltf-webgpu `feature/khr-audio`, generated by `scripts/make-drum-kit.mjs`) delivers the full experience with a **procedural** stylized kit instead of a downloaded model — no direct-download CC0 glTF drum kit was available without auth walls, and procedural generation gives CC0-by-construction licensing plus perfect per-drum nodes/pivots:
- 8 playable pieces (kick, snare, high/mid/floor toms, hi-hat, crash, ride) + non-selectable chrome hardware (`KHR_node_selectability`)
- 8 synthesized drum voices encoded to **MP3 in-process** (`@breezystack/lamejs`) — fully conformant with the KHR_audio_emitter base codec
- per-drum positional emitters, air absorption, tuned `reverbLevel` sends (kick dry → crash wet) into a `smallRoom` environment
- `event/onSelect` → `pointer/set(sources/{i}/playing)` per drum; ~180 KB total
- Passes `validate-layered.mjs`; play at `viewer.html?model=/examples/drum-kit/drum-kit.gltf`

Remaining phases below are now *upgrades* to v1 rather than prerequisites.

## Phase 1 — Real drum kit model (optional upgrade)

1. Source a CC0/CC-BY drum kit (Sketchfab CC0 search, Poly Haven, BlenderKit CC0; verify license allows redistribution in a Khronos-adjacent demo). Requirements: separate meshes (or at least separate named nodes) for kick, snare, hi-hat, 2–3 toms, crash, ride.
2. If it arrives as FBX/blend: convert via Blender → glTF export; ensure each drum is its own node (rename nodes `Kick`, `Snare`, …), sane pivot points, PBR materials.
3. Optimize: meshopt/draco optional; target < 10 MB with textures.

## Phase 2 — Sounds

1. CC0 drum samples (freesound.org CC0, or synthesize like the PoC generator). One-shot per drum; 2–3 velocity layers if we get ambitious (velocity = distance from drum center at hit → gain, cheap "velocity" from `selectionPoint`).
2. Encode per spec: MP3 for the base-spec story (one-shots don't loop, so MP3's gapless-loop weakness doesn't bite here — worth saying in the demo notes) — this makes the asset **fully KHR_audio_emitter-conformant** on the codec axis.
3. One `source` per sample, non-autoplay; one positional `emitter` per drum node (omnidirectional, inverse, refDistance ~0.5 m, maxDistance ~30 m; cymbals get `airAbsorption` + slight `coneOuterCutoff` for realism).

## Phase 3 — Interactivity graph

Per drum: `event/onSelect (nodeIndex=drum)` → `pointer/set(sources/{i}/playing = 1)`.
Enhancements, all spec-legal today:
- `flow/sequence` + second `pointer/set` to animate a "hit" scale pulse via `/nodes/{i}/scale` (or trigger a small glTF animation with `animation/start`).
- Velocity: `event/onSelect.selectionPoint` → `math/*` distance from center → `pointer/set(sources/{i}/gain)` before triggering.
- Hi-hat open/closed toggle: `variable/set` + `flow/branch` choosing between two sources — shows switch-container-like behavior in pure KHR_interactivity.

## Phase 4 — Environment

- Scene default environment: `preset: "smallRoom"`, `mix ~0.25`, per-drum `reverbLevel` tuned (kick drier, cymbals wetter).
- Optional zone demo: a "garage" box zone around the kit vs outdoor default — walk the camera out and hear the room change (shows KHR_audio_environment zones on a musical asset).

## Phase 5 — Packaging & messaging

- Ship as `.glb` (bufferView audio) *and* `.gltf + files`; validate with AudioGraphJS `validate-layered.mjs`.
- Record a short capture (viewer + audio) for the issue #2561 thread / WG meeting.
- Write-up: "A playable instrument in pure glTF" — lands the messaging pillars: layered adoption (works sound-less in any viewer, spatial in emitter-aware viewers, full experience with interactivity), and makes the E1 gap concrete with a working counterfactual.

## Open items to resolve during build

- The `playing` trigger pointer: keep as viewer extension, or draft it as a one-paragraph proposal (`KHR_audio_emitter` Object Model addition: writable bool `playing`, restart-on-rising-edge semantics) to attach to the E1 feedback. Recommend the latter — the drum kit *is* the use-case evidence.
- Polyphony: retriggering currently overlaps voices (correct for cymbals, debatable for kick); consider max-instances note → ties into voice-management feedback (E6/P10).
- MP3 one-shot latency (decoder padding delays onset ~25–50 ms): measure; if audible, this becomes *more* codec-feedback ammo (Opus has no such padding).
